# Encryption Key Rotation Runbook

อัปเดต 12 ต.ค. 2026: เปลี่ยนกุญแจต้นทางตามแผนข้อมูลทดลองที่เจ้าของอนุมัติแล้ว รักษา plaintext เดิม 14 ค่า แทนค่าอ่านไม่ได้ 24 ค่าด้วย MOCK และอ่านด้วยกุญแจใหม่ครบ 38 ค่า ดู [สถานะจริงและหลักฐาน](launch-main-current.md) วิธี generic rotation ด้านล่างไม่ได้ใช้แทนเครื่องมือ transition ที่ซ้อมและตรวจ rollback แล้ว

เอกสารนี้ใช้สำหรับเปลี่ยน `ENCRYPTION_KEY` โดยไม่ทำให้ข้อมูลเดิมที่เข้ารหัสไว้สูญหาย

## หลักความปลอดภัย

- ห้ามเปลี่ยน `ENCRYPTION_KEY` ใน Production ทันทีหากยังไม่ได้ยืนยันว่าข้อมูลเดิมถอดรหัสด้วยคีย์เก่าได้
- ห้ามแสดง product key, password, email ลูกค้า หรือข้อมูลลับใน log
- ต้องมี backup ฐานข้อมูลที่กู้คืนได้ก่อนใช้โหมด `--apply`
- ใช้ `OLD_ENCRYPTION_KEY` เฉพาะช่วง dry-run/apply rotation เท่านั้น
- หลังหมุนคีย์สำเร็จ ให้ลบ `OLD_ENCRYPTION_KEY` ออกจากเครื่องและ environment ที่ไม่จำเป็น

## ขั้นตอนแนะนำ

1. สร้าง backup ฐานข้อมูลจาก Supabase/Vercel Storage Provider และทดสอบว่ากู้คืนได้
2. ตั้งค่าในเครื่องสำหรับตรวจสอบเท่านั้น:
   - `OLD_ENCRYPTION_KEY` = คีย์ที่ระบบใช้อยู่เดิม
   - `ENCRYPTION_KEY` = คีย์ใหม่ที่สร้างจาก `scripts/generate-encryption-key.ts`
3. ตรวจสถานะข้อมูลแบบอ่านอย่างเดียว:

```bash
npm run audit-encryption
```

4. ตรวจแผนหมุนคีย์แบบไม่เขียนฐานข้อมูล:

```bash
npm run rotate-encryption-key
```

5. หาก dry-run ไม่มีรายการที่ถอดรหัสไม่ได้ และมี backup แล้ว จึงค่อยรันโหมดเขียนจริง:

```bash
npm run rotate-encryption-key:apply
```

6. ตรวจซ้ำหลังหมุนคีย์:

```bash
npm run audit-encryption
```

7. อัปเดต `ENCRYPTION_KEY` ใหม่บน Vercel เท่านั้น หลังข้อมูลในฐานข้อมูลหมุนคีย์แล้ว
8. ห้ามตั้ง `OLD_ENCRYPTION_KEY` บน runtime ปกติ ยกเว้นมีงาน one-off ที่จำเป็นและได้รับอนุญาต

## Rollback

หากโหมด `--apply` ล้มเหลว transaction จะ rollback โดยอัตโนมัติและสคริปต์จะหยุดทันที
หากพบปัญหาหลัง commit ให้กู้คืนจาก backup ที่สร้างไว้ก่อนเริ่มงาน แล้วตรวจด้วย `npm run audit-encryption` อีกครั้ง

## แผนหลังเจ้าของยืนยันว่ารายการทั้งหมดเป็นข้อมูลทดลอง — 11 ต.ค. 2026

เจ้าของยืนยันว่าออเดอร์/สินค้าที่ขายทั้งหมดเป็นการทดลอง และอนุญาตให้ซ้อมบนฐานจำลอง ยังไม่อนุญาตเปลี่ยนฐานจริง/กุญแจ Vercel หรือ deploy

ผลซ้อม: [launch-test-data-rekey-rehearsal-latest.json](launch-test-data-rekey-rehearsal-latest.json)

- กู้ไฟล์สำรองเดิมลง localhost แล้วตรวจจำนวนแถว/hash ตรงก่อนเริ่ม
- ย้าย encrypted values ที่ถอดได้ 14 ค่าไปกุญแจสุ่มใหม่โดย plaintext เดิมคงอยู่
- แทน encrypted values ที่ถอดไม่ได้ 24 ค่าด้วยข้อมูล MOCK อย่างชัดเจน เฉพาะสำเนาทดสอบ ไม่อ้างว่ากู้ข้อมูลเดิมได้
- กุญแจใหม่อ่านครบ 38 ค่า กุญแจเดิมอ่าน ciphertext ใหม่ไม่ได้
- จำนวนแถวทุกตาราง คอลัมน์ที่ไม่ใช่ข้อมูลลับ ยอดเงิน สถานะออเดอร์ isSold และ orderId คงเดิม ไม่มีการคืนสินค้าที่ขายแล้วเข้าสต็อก
- ซ้อม transaction rollback แล้ว hash ทั้ง 9 ตารางตรงก่อนเปลี่ยน ตรวจ foreign key ของ stock/order ผ่าน
- กุญแจใหม่ใช้ชั่วคราวในหน่วยความจำ ไม่ถูกบันทึกลง .env หรือ Vercel สำเนาฐานชั่วคราวลบแล้ว

เครื่องมือ: scripts/rehearse-test-data-rekey.ts --confirm-all-data-is-test ใช้สำเนา localhost เท่านั้น ไม่มีโหมดเขียนฐานจริง

แผนดำเนินการจริงในอนาคต (ยังไม่ทำ):
1. ตรวจ drift/ข้อมูลใหม่และยืนยันอีกครั้งว่าเป็นข้อมูลทดลองทั้งหมด สำรองใหม่ทั้งข้อมูลและ configuration พร้อมซ้อมกู้คืน เก็บกุญแจเก่าไว้กับหลักฐาน rollback อย่างปลอดภัย
2. เลือกว่าจะรักษารายการทดลองเดิมโดยแทนช่องที่เปิดไม่ได้ หรือเริ่มร้านด้วยข้อมูลสินค้าใหม่ที่เจ้าของตรวจแล้ว ห้ามนำ MOCK หรือสินค้าที่ขายแล้วกลับไปเปิดขาย
3. จัดทำ mapping ที่ตรวจสอบได้สำหรับข้อมูลจัดส่งและสต็อกที่แทนค่า ไม่ใช้เครื่องมือซ้อมนี้เป็น production migration
4. เตรียมกุญแจจริงใหม่และเก็บอย่างปลอดภัย พร้อมแผนอัปเดตฐานและ runtime ในช่วงปิดรับคำสั่งซื้อ ต้องอนุมัติการย้ายจริงและ deploy แยกก่อนเริ่ม มิฉะนั้นฐานที่ใช้กุญแจใหม่กับเว็บที่ยังใช้กุญแจเก่าจะไม่สอดคล้องกัน
5. หลังย้ายบน transaction ตรวจข้อมูลทั้งหมดก่อน commit จากนั้นอัปเดต environment/runtime ตามแผน ตรวจ end-to-end แบบไม่รับเงินจริง และพร้อม rollback ฐาน+runtime กลับคู่เดิมหากตรวจไม่ผ่าน
6. อนุมัติเปิดขายต่างหากเมื่อ SMTP, sandbox, commerce migration, hosting/worker และการทดสอบครบ

ขณะนี้ไม่ต้องค้นกุญแจเก่าต่อเพื่อกู้ข้อมูลทดลองที่เจ้าของยอมให้แทนบนสำเนา แต่ฐานจริงยังคง 24 ค่าเดิมที่เปิดไม่ได้ ยังไม่ถือว่าการหมุนกุญแจของระบบจริงเสร็จ
