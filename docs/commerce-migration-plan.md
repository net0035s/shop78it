# แผนย้ายโครงสร้างข้อมูลและผลดำเนินการ

อัปเดต 12 ต.ค. 2026: เจ้าของอนุมัติและดำเนิน migration ต้นทางแล้ว พร้อมกุญแจใหม่/guard/Production แบบปิดรับเงินจริง ดูสถานะปัจจุบันที่ [launch-main-current.md](launch-main-current.md) ข้อความวันที่เก่าด้านล่างเป็นประวัติแผนก่อนทำจริง

วันที่ 5 กันยายน 2026 งานรอบนี้สร้างและทดสอบ SQL กับข้อมูลจำลองเท่านั้น ไม่เชื่อมฐานข้อมูลจริงเพื่อแก้ไข ไม่สำรองฐานข้อมูลจริง ไม่เปลี่ยน ENCRYPTION_KEY และไม่ deploy

## สิ่งที่เพิ่ม

- ตาราง PaymentAttempt, OrderAccessSession, OrderAccessChallenge, NotificationJob, OrderAuditEvent และ RateLimitBucket
- วันหมดอายุ/วันรับเงิน สถานะการจองสินค้าและคูปองบนออเดอร์
- snapshot ชื่อ รูปภาพ และชนิดจัดส่งใน OrderItem โดยรักษาราคาเดิมที่เคยซื้อ
- ตัวเชื่อม DeliveryItem กับ OrderItem/stock และดัชนีป้องกันเลขอ้างอิงรับเงินหรือ stock ID ซ้ำ
- SQL baseline จาก schema เดิม และ additive migration แยกต่างหาก ไม่มี DROP ตารางข้อมูลธุรกิจ

ไฟล์ baseline.prisma เป็น schema เดิมที่เก็บไว้ก่อนแก้ ไม่ใช่หลักฐานว่า schema บนฐานข้อมูลจริงตรงกันแล้ว

## เงื่อนไขก่อนนำไปใช้จริง

1. ตรวจและอนุมัติแผนกุญแจใน encryption-key-rotation.md พร้อมตรวจสถานะข้อมูลที่เข้ารหัส ห้ามแก้ environment key ให้ผ่าน validation เฉย ๆ เพราะอาจทำให้ข้อมูลเก่าอ่านไม่ได้
2. สำรองฐานข้อมูลแบบเข้ารหัส เก็บกุญแจที่ใช้อ่านแยกจาก backup ตรวจจำนวนแถว และทดลอง restore ลงฐานข้อมูลแยกจนอ่านข้อมูลตัวอย่างได้ บันทึกที่เก็บ วันเวลา และผู้ตรวจ ไม่เก็บ backup/กุญแจใน Git
3. หยุดการสร้างออเดอร์ การรับเงิน และ worker ระหว่างเปลี่ยนโครงสร้าง ตั้ง PAYMENTS_ENABLED=false และหยุดตัวแอปที่อาจเขียนฐานข้อมูล
4. ตรวจ schema จริงกับ prisma/baseline.prisma แบบ read-only หากมี drift ต้องจัด SQL เพิ่มและทดลองกับสำเนาก่อน ห้าม baseline resolve ทั้งที่ schema ไม่ตรง
5. ทดลอง migration บนสำเนาจาก backup ตรวจยอดเงิน จำนวนออเดอร์ คีย์ที่ขายแล้ว และการถอดรหัสก่อน/หลัง การหมุนกุญแจต้องเป็นแผนแยก ไม่ทำพร้อม SQL นี้
6. จัดการออเดอร์เก่าที่มีผลรับเงินไม่ชัดเจนตามส่วนด้านล่าง ตรวจยอดรวมคูปองกับรายการที่ใช้จริงก่อนเปิดรับออเดอร์ใหม่
7. หลังผู้รับผิดชอบอนุมัติผล rehearsal จึงวางแผนรัน migration จริงและเปิดใช้งานในงานถัดไป

## วิธีใช้ migrations สำหรับผู้ดูแลเมื่อผ่านเงื่อนไขแล้ว

ฐานข้อมูลใหม่ว่าง: ใช้ migrations ทั้ง baseline และ commerce_safety

ฐานข้อมูลเดิม: ตรวจว่า schema ตรง baseline ก่อน แล้วทำเครื่องหมาย baseline ว่า applied จึงใช้ additive migration ห้ามรัน baseline CREATE TABLE ซ้ำกับฐานข้อมูลเดิม

คำสั่งอ้างอิง (ยังไม่ได้รันกับฐานข้อมูลจริง):

```
npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/baseline.prisma --exit-code
npx prisma migrate resolve --applied 202609050001_baseline
npx prisma migrate deploy
```

คำสั่ง diff ต้องชี้ environment ที่ถูกต้องและเป็นการอ่านอย่างเดียว ส่วน resolve/deploy เป็นการเขียน ต้องทำหลัง backup และอนุมัติแผนจริงแล้วเท่านั้น อย่าใช้ migrate reset หรือ db push แทน

## ข้อมูลเก่าที่ต้องตรวจเป็นพิเศษ

- วันรับเงินเดิมไม่มีข้อมูลจากผู้ให้บริการ จึง backfill จาก updatedAt พร้อม paidAtEstimated=true ยอดเก่าตามวันเป็นค่าประมาณ ต้องกระทบยอดบัญชีก่อนใช้เป็นรายงานทางการเงิน
- snapshot ชื่อ/รูป/ชนิดจัดส่งเดิมเติมจากสินค้าปัจจุบัน ราคา OrderItem.price เดิมไม่เปลี่ยน ไม่สามารถสร้างชื่อสินค้าประวัติที่ไม่ได้เก็บไว้ขึ้นมาใหม่ได้
- pending ที่มี DigitalStock.isSold=true ถูกย้ายเป็น payment_review และสร้างรายการ legacy สำหรับตรวจสอบ ไม่คืนคีย์ที่ขายแล้วและไม่เปิดให้จ่ายซ้ำอัตโนมัติ
- รายการส่งมอบเดิมที่ไม่มี orderItemId จะคงไว้ และให้ร้านตรวจเองเมื่อกู้การจัดส่ง เพื่อไม่ออกคีย์ซ้ำจากการเดาจับคู่
- บิลเก่าที่ยังไม่ได้จองคูปองจะตรวจและจองสิทธิ์อีกครั้งก่อนเริ่มรับเงิน หากหมดสิทธิ์ต้องสร้างบิลใหม่
- สต็อกอ่านไม่ได้จะถูกกักไว้กับออเดอร์และขึ้น needs_manual_delivery ร้านต้องตรวจข้อมูล/กุญแจก่อนแก้ ไม่ปล่อยกลับขายเอง

## สิทธิ์ Supabase Data API

วันที่ 11 ตุลาคม 2026 หลังเจ้าของอนุมัติ ได้ใช้ Supabase migration 20261011064132 / lock_down_shop_data_api เพื่อเปิด RLS และถอน anon/authenticated/PUBLIC ของ 9 ตารางเดิมแล้ว ไม่ได้ใช้ baseline/commerce schema migration จริง และไม่ได้เปลี่ยน rows/กุญแจ ดู [หลักฐาน](launch-rls-change-latest.json)

commerce_safety ที่ยังไม่ใช้จริงเพิ่ม RLS และถอน public grants ของ 6 ตารางใหม่แล้ว ทดสอบกับ fixture ที่จำลอง Supabase default grants ให้ PUBLIC/anon/authenticated ผ่าน ข้อมูลเดิมและการทำงานของ Prisma/commerce คงเดิม หลังย้ายจริงต้องตรวจ grants/advisors ทั้ง 15 ตาราง และทดสอบ server role ตาม runbook RLS/GRANT ไม่อยู่ใน Prisma datamodel จึงห้ามถือว่า migrate diff ผ่านแล้วเท่ากับตรวจสิทธิ์ครบ ต้องจัดช่วงบำรุงรักษาและปิดการเข้าถึง Data API ที่ไม่จำเป็นระหว่างย้ายตามแผนที่เจ้าของตรวจแล้ว

## ค่าที่ต้องตรวจใน environment

PAYMENTS_ENABLED เริ่มที่ false; ENCRYPTION_KEY ต้องผ่านแผนและตรวจการถอดรหัส; NEXT_PUBLIC_SITE_URL ต้องเป็นโดเมนร้านจริงที่ใช้ HTTPS; EMAIL_USER/EMAIL_PASS ต้องส่งลิงก์ยืนยันได้; CRON_SECRET ต้องตั้งทั้งฝั่งเรียกและเซิร์ฟเวอร์; ค่าผู้ให้บริการรับเงินต้องเป็นช่องทางที่อนุมัติแล้ว

Cron ใช้ /api/cron/clear-unpaid ทุก 5 นาที (อีก endpoint ใช้ logic เดียวกัน) ต้องตรวจว่าแพลนโฮสต์รองรับความถี่นี้ หากไม่รองรับให้จัด scheduler ที่รองรับก่อนเปิดจริง API ยังคงปฏิเสธบิลหมดอายุแม้ cron ยังไม่ทำงาน แต่การคืนสต็อกจะรอ worker

คิวแจ้งเตือนลองใหม่พร้อมหน่วงเวลาไม่เกิน 6 ครั้งต่อ job และเก็บผลส่งจริง หากหมดจำนวนครั้งให้ร้านตรวจค่าระบบและใช้การส่งอีเมลใหม่ในหลังบ้าน ไม่ถือว่างานส่งสำเร็จจากการเพิ่มคิวอย่างเดียว

## การตรวจผลรับเงินที่ไม่ชัดเจน

เปิดออเดอร์ในหลังบ้าน ตรวจบัญชีหรือรายงานผู้ให้บริการก่อนบันทึกผลพร้อมหมายเหตุ รอคำขอเดิมจบอย่างน้อย 60 วินาที เลขอ้างอิงต้องใช้รูปแบบเดียวกับระบบ เช่น slipok:ธนาคาร:เลขรายการ หรือ truemoney:ค่า hash ของ voucher ที่อยู่ใน requestKey; รายการเก่าใช้ legacy:เลขอ้างอิงที่ตรวจยืนยันแล้ว

ยอดขาด/ยอดเกินไม่ถูกยืนยันเป็นชำระครบอัตโนมัติและไม่เปิดจ่ายซ้ำเอง ต้องจัดการคืนเงิน/กระทบยอดภายนอกตามกระบวนการร้านโดยผู้มีอำนาจ ระบบรอบนี้ไม่ได้เพิ่มฟีเจอร์คืนเงินจริง

## การย้อนกลับ

ถ้ายังไม่เปิดรับรายการใหม่ ให้คืนแอปและฐานข้อมูลจาก backup ที่ทดลอง restore แล้วเป็นชุดเดียวกัน ถ้ามีรายการใหม่หลังเปลี่ยนระบบ ต้องกระทบยอดและเก็บหลักฐานรับเงินก่อน ห้ามลด schema หรือ restore ทับยอดล่าสุดทันที และห้ามลบกุญแจเก่าก่อนยืนยันว่าข้อมูลทั้งหมดอ่านได้
